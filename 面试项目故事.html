三、完整 STAR 故事(面试 5 分钟版)

S — Situation(背景,30 秒)

公司自研的实验室信息化管理平台(CMS + ELN,面向生物/化学实验室)业务迭代快:物质注册、样品管理、审批流、编号规则、出库等模块频繁上线功能。但整个平台是纯手工回归——每次发版,测试同事要手动把核心流程点一遍,一轮就要【X 人天】,而且平台页面大量使用 iframe 弹窗和 canvas 画布,操作繁琐、重复劳动多、还容易漏测。团队里之前没有可用的 UI 自动化框架。

T — Task(任务,20 秒)

我的任务是:从零搭建一套可持续维护的 UI 自动化框架,把核心业务链路自动化,让回归测试从"手工点一遍"变成"一条命令跑完出报告"。要求三条:用例可维护(页面改版能低成本跟进)、可重复执行(不能跑一次就脏数据)、失败可追溯(出问题能快速定位)。

A — Action(行动,3 分钟,分四段讲)

第一步:技术选型 + 分层架构。对比了 Selenium 和 Playwright 后选了 Playwright,理由是自动等待机制、原生支持多页面/iframe、以及 page.request 可以直接复用登录态调接口。框架按六层拆分:locator(元素定位)、object(页面对象)、data(测试数据)、config(环境配置)、utils(工具)、testcases(用例),每一层职责单一,页面改版只动 locator 和 object 层。

第二步:解决这个系统最难自动化的三个点。① 平台有大量 iframe 弹窗,原生 Playwright 操作 frame 和 page 的 API 不一致,写起来很别扭。我封装了一个 baseframe 类,让 frame 对象拥有和 Page 完全一致的操作方法(click / fill / wait_for 等),还支持嵌套 iframe,业务代码里几乎感觉不到在操作 frame。② 可视化模块是 canvas 画布,没有 DOM 元素可定位,我实现了基于相对坐标的点击/双击/右键封装。③ 定位器直接用字符串散落在业务代码里很难维护,我设计了一套定位描述 DSL——("role", "button", "保存")、("selector", ".xxx", {"has_text": "xx"}) 这样的元组,由 BasePage 统一翻译成 Playwright Locator,业务代码与具体定位方式解耦。

第三步:用例编排,把 60 步业务链路串起来。这个系统前后业务强依赖:要先建模板才能建项目、注册了物质才能登记样品、登记了样品才能申领出库。单条用例孤立跑没意义。我的做法是:用 pytest 的 cache 机制做跨用例数据传递——上游用例把"项目名、批号、样品名"写入 cache,下游用例通过 pytest_generate_tests 钩子动态参数化读取;再用 @pytest.mark.order 全局编排执行顺序,最终一条命令就能跑完"模板 → 项目 → 物质注册 → 审核审批 → 样品登记 → 领样车申领 → 出库"全链路。同时所有测试数据(批号、DNA/RNA 序列、项目名)都是运行时随机生成的,跑多少遍都不会数据冲突。

第四步:稳定性 + 可追溯性。两件事:一是尽量不用固定 sleep,改用 expect_response 监听关键接口响应——动作发起后等接口返回 200 才继续,既快又稳;接口响应码和数据还自动 attach 到 Allure 报告里,用例失败时打开报告直接能看到 UI 走到哪、接口返回了什么。二是成员权限这种需要双账号的用例,用 browser.new_context() 创建隔离的浏览器上下文,主账号开/关权限,小号验证数据可见性,互不串号。报告层用 Allure 的 epic/feature/story 三级分类,失败自动截图。

R — Result(结果,30 秒)

最终框架约 7600 行代码、50 个用例,覆盖 7 个核心业务模块,一条命令跑完整条业务链路并自动生成 Allure 报告。回归执行从手工【X 人天】降到【X 分钟/小时】,并且【在此填入真实产出,如:发现了 N 个手工回归漏掉的 bug / 支撑了 N 次发版回归】。过程中最大的收获:自动化框架的难点从来不是"能跑起来",而是用例间依赖编排和失败可诊断——这也是我花时间最多的地方。

六、面试官高频追问 + 参考回答

Q1:为什么选 Playwright 而不是 Selenium?自动等待机制减少显式 sleep;原生支持多页面、多 iframe 上下文切换;page.request 能复用登录态直接发接口(造数、清理、断言);trace 录制方便排查。对我们这种 iframe 特别多的平台,Playwright 的 frame 支持明显更顺。

Q2:用例之间有数据依赖,为什么不各自造数据独立跑?早期也纠结过。但这个平台造一条数据链路太长(建模板→建项目→注册→审批,一条链路下来几十步),每个用例各自造数会导致执行时间翻好几倍,而且大量前置步骤本身重复。所以折中方案:链路上游的数据由对应用例产出并写入 cache,下游消费;配合全局 order 保证顺序。代价是牺牲了用例独立性——我知道这是取舍,改进方向是 pytest-dependency 或者把数据准备下沉到 fixture 层做 session 级共享。

Q3:pytest cache 传数据的缺点?cache 是跨 session 持久的,脏缓存会导致数据错乱,所以 cache_dir 指向了专用的 record_test_data 目录,跑全量前会清理;另外这种方式不支持并行执行,这也是我下一步要解决的。

Q4:pydantic 在这个项目里解决什么问题?YAML 里的测试数据加载后立即做类型校验,字段写错类型(比如把数字写成字符串)在数据加载时就报错,而不是跑用例跑到一半才炸;环境配置同理,切换环境时用户名密码这些必填项缺失会立刻失败。

Q5:用例失败了怎么排查?三层:一看 Allure 报告——失败步骤、当时的页面截图、关键接口的请求 URL 和状态码附件;二看分级日志,每个操作都有 debug/info/error 三级日志带文件名和行号;三看接口响应本身,很多问题(比如 SSO token 延迟导致的 401)不看接口根本发现不了。

Q6:框架有什么不足/下一步改进?① 目前不支持并行(用例间有依赖),后续可以把全链路拆成"数据准备 fixture + 独立用例"的形态;② 还没接入 CI,计划上 Jenkins/GitLab CI 做定时回归;③ 接口断言目前主要看状态码,可以加强响应体字段断言;④ 元素定位 DSL 可以再补一层自动截图 + 失败自愈重试。

Q7:随机数据不会造成系统数据堆积吗?数据命名统一带 auto_test 前缀 + 日期,方便筛选;框架里也有基于接口的清理脚本(delete_data.py 通过 page.request 调删除接口),跑完一轮可以按记录的数据批量清理。

Q8:如果一个页面元素定位变了,你要改几个地方?只改 locator 层对应模块的一个常量。业务方法引用的都是定位描述,不直接写 CSS,这是设计 DSL 的初衷。
