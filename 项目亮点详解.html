二、等待机制(稳定性设计)★★★

1. 接口响应等待(核心亮点)

object/basepage.py:146 wait_according_to_the_interface(url, action):

with self.page.expect_response(lambda response: response.url == url, timeout=timeout) as response_info:
    action()
# 响应 200 → 动作执行成功;非 200 → 抛异常

设计动机:点"保存"按钮后,数据什么时候真正落库?固定 sleep(2) 的问题:网络快时浪费 2 秒,网络慢时 2 秒不够。监听保存接口的响应,200 返回才继续——又快又稳,而且把"接口没响应/报错"直接暴露成用例失败。

面试讲法:讲清 sleep 的三个问题(浪费时间/不稳定/失败后不知道卡在哪),再讲 expect_response 怎么解决。

可能追问:接口 URL 变了怎么办?→ 接口常量统一在 config/setting.py,只改一处。

2. 响应捕获 + Allure 附件

utils/get_response.py:注册 page.on('response') 监听,执行动作后收集所有匹配响应,取最后一个,把 URL 和状态码 attach 进 Allure 报告。

面试讲法:"用例失败时,打开 Allure 报告能看到这个动作触发了哪个接口、返回了什么状态码——定位失败从'猜'变成'看'。"

3. 分层等待策略

  • 页面级:wait_for_load_state('networkidle') 等页面资源加载完(conftest.py:35)
  • 元素级:loc.wait_for(state='visible'/'attached') 等元素出现/挂载(basepage.py:91)
  • 接口级:expect_response 等业务动作完成
  • 导航级:wait_for_url 等跳转

面试讲法:三层等待各司其职,能不用 sleep 就不用 sleep。

诚实提示:代码里仍有少量 wait_for_timeout(如 baseframe 内 200ms 微等待、token 延迟 2000ms)。面试被问到就说:"个别场景存在对时机的硬等待,比如 SSO token 写入有延迟,曾出现偶发 401,当时加了 2 秒等待作为临时方案,这类硬编码我标注了 TODO 计划改成接口轮询。"——这反而是个很好的踩坑故事(见第五节)。

三、数据设计:定义 → 校验补齐 → 自动生成 → 流转复用(全流程)★★★

一句话主线:数据用 YAML 定义(人人可读可改)→ pydantic 加载即校验(YAML 没填的自动补)→ 运行时随机生成(可无限重复执行)→ pytest cache 在用例间流转(依赖用例独立跑、前置数据一次生成反复用、跑一半断了还能接着跑)。

1. YAML 定义数据:非业务人员也能看懂、能自己填

data/yaml_data/ 下 12 个 yml 按模块分目录,字段全是业务语言:

  • single_register.yml:add_module_list 直接列 12 种模块名("基本信息""计算化学信息""物化信息"…),register_amount: "100"
  • sample_list.yml:current_amount、sample_form、sample_tube_type

面试讲法:"测试数据不写在代码里,写在 YAML 里,字段名就是业务词。业务同学或手工测试同事不用懂 Python,打开文件就知道'注册量填 100'是什么意思,想改测试数据直接改文件。这是数据驱动的第一步:数据与代码分离。"

补充分层:不常变的数据再分一层——固定参数(test_params.json)、项目-模板-审核映射(projects.json,5 种注册类型 × 7 种审核类型)单独放 record_test_data/test_record/,全模块共用,改参数不翻代码。

2. pydantic 加载即校验 + 空值自动补齐:YAML 没填的,模型自己补

每个 yml 对应一个 pydantic 模型(data/pydantic/*),from_yaml() 加载即 model_validate:

  1. 类型安全:YAML 里字段类型写错,数据加载时就报错,不会跑到用例一半才炸
  2. 空值自动生成——4 个模型都有 field_validator,YAML 留空 = 让框架自动生成:
    • 批号空 → auto_test_batch_member_时间戳(single_register.py:15、batch_register.py:17)
    • 样品名空 → autotest_时间戳(sample_list.py:17)
    • 笔记本名空 → auto_test_时间戳(eln.py:15)

面试讲法:"YAML 里留空的字段不是'没配好',而是约定'让框架自动生成'——校验器在加载时补齐带时间戳的默认值。用例代码从头到尾不关心数据从哪来。业务人员填 YAML 时:会填就填,不会填留空,照样能跑。"

可能追问:为什么不用 JSON?→ YAML 可读性好、支持注释,适合人工维护;类型校验靠 pydantic,JSON 做不到。

3. 运行时随机生成:数据天然可重复执行(为 CI/CD 做准备)

utils/auto_generated_data.py:DNA/RNA 随机序列(3~1000 个碱基)、批号(类型缩写_月日时分秒)、项目名(auto_test_类型项目(月日))、注册量(随机值 + 随机单位)。

面试讲法:"CI 上每天定时跑同一套用例,数据名如果固定,第二天就撞了。我的方案是所有业务名运行时随机生成 + auto_test 前缀统一标识,同一套用例每天跑也不会数据冲突;环境配置独立在 yml 里,切换环境改配置不动代码;配合 main.py 一键运行——数据侧已经为接入 CI 做好了准备。"

诚实边界(主动说加分):离 CI 还差最后两步:浏览器 headless=False 目前写死在 conftest 里,接入 CI 要参数化;用例间有依赖暂不支持并行。这两条我列为改进项。

4. cache 数据流转:依赖用例独立运行、一次生成反复用、断点续跑

能力实现代码证据
上游写request.config.cache.set("compound_sequence_project_name", 项目名)test_sample_cart.py:42、test_member_permission_management.py:61
下游读request.config.cache.get(...) + pytest_generate_tests 动态参数化conftest.py:46、test_eln.py:20
独立运行兜底关键用例带"缓存没有就现场造"分支test_sample_cart.py:31 "如果缓存中没有样品名称,先登记一个样品"
一次生成反复用cache 落盘持久化,跨 session 不丢pytest.ini cache_dir + record_test_data/v/ 30+ 个键
断点续跑缓存跨 session 持久:昨天跑到一半,今天单跑剩余用例数据还在同上

面试讲法(重点故事):"这个系统业务强依赖:建模板→建项目→注册物质→登记样品→申领出库,单条用例孤立跑没意义。我的方案:上游用例把'项目名、批号、样品名'写进 pytest cache,下游用例通过 pytest_generate_tests 钩子动态参数化——批量注册用例的参数就是上游建好的 5 种类型的项目名。cache 是落盘的:前置用例只跑一次,数据后面反复用;全量跑一半断了,明天单跑剩余用例,缓存里的数据还能接上。部分关键用例还自带兜底:缓存没有就现场造一条,保证依赖用例也能独立运行。"

可能追问:

  • Q: 依赖用例真的都能独立跑吗?→ 如实答:"带兜底分支的可以(比如领样车用例缓存没有样品就自己登记一个);参数化用例不行,缓存为空时 conftest 会显式报错'没有记录到项目名称'——这是故意的,'依赖缺失'要显性失败,而不是悄悄拿错误数据跑。"
  • Q: 缓存数据会脏吗?→ auto_test 前缀 + 时间戳天然不冲突;record_test_data/ 在 .gitignore 不进版本库;跑全量前清缓存。
  • Q: 能并行吗?→ 不能,有依赖才有全局编排,这是取舍,改进方向是 pytest-dependency 或数据准备下沉到 fixture。

备注:utils/set_to_test_record.py 是早期写的一个按天 JSON 记录模块,实际未接入用例(pytest cache 落盘持久化已覆盖该需求),面试不必主动提及。

四、其余高价值亮点

1. 定位描述 DSL ★★★

basepage.py:11 find():元组描述定位方式,统一翻译成 Locator:

  • ("text", "保存") → get_by_text
  • ("role", "button", "保存") → get_by_role(exact=True)(注释里还专门处理了文本里 / 被当正则的问题)
  • ("selector", ".xxx", {"has_text": "xx"}) → locator.filter()
  • ("placeholder", "请输入") → get_by_placeholder

面试讲法:"业务代码引用的定位描述与具体定位策略解耦。页面改版时,业务用例一行不用改,只改 locator 层。而且把'这个按钮是 role 定位还是 selector 定位'的决策权收口到一层,新人写用例不容易写出脆弱的 XPath。"

2. iframe 操作层 ★★★

object/baseframe.py:让 frame 像 page 一样操作(click/fill/wait_for/get_frame 全有),支持嵌套 iframe(frame 里再 get_frame)。还做了个细节:选择器如果是纯 class 名(如 "icon-close default")自动补点转 CSS。

面试讲法:"平台弹窗几乎全是 iframe,原生 Playwright 里 frame 和 page 两套 API,业务代码里要一直区分'我现在在 frame 里吗'。封装后业务层无感,这个类写了 228 行,支撑了全部 50 个用例。"

3. Excel 导出 vs 接口数据比对(测试设计能力)★★★

testcases/data_center/test_data_export.py + object/data_center/data_center.py:123:

  1. 监听物质列表接口 → 拿到接口数据(权威数据源)
  2. 页面导出 Excel → openpyxl 读回
  3. compare_material_data(excel_wb, api_data) 逐条比对 → 差异列表为空才通过

面试讲法:这是全项目里最能体现"测试设计"的用例:"导出的文件不是'能打开'就行,要和接口数据逐条比对——页面展示、接口返回、导出文件三者的数据一致性。这个用例还参数化了两种视图模式(全部数据/按物质分组)。"

4. 双账号权限验证 ★★★

testcases/group_management/test_member_permission_management.py:

  • 参数化 [False, True]:先关权限跑一遍(验证不可见),再开权限跑一遍(验证可见)——正反两面断言
  • 小号用 browser.new_context() 独立上下文登录,与主账号隔离,不串号
  • 自定义异常 ElementNotFoundError 捕获"找不到元素"作为断言依据(权限关=找不到=通过)

面试讲法:"权限测试的难点:第一,要两个账号视角;第二,'不可见'本身就是断言目标——不能因为找不到元素就报错,要把'找不到'设计成预期结果。"

5. 化学结构编辑器自动化(indraw)★★

utils/indraw.py:进入编辑 → 切进 iframe[src*='indraw'] → 点击苯环工具 → 在 .dynamic canvas 的 (50,50) 相对坐标画出苯环 → 关闭编辑器。ELN 用例里注册到 CMS 后还要断言 SMILES 结构式。

面试讲法:这是最惊艳的细节之一:"化学结构编辑器是 iframe 套 canvas,普通定位器完全失效。我用相对坐标在画布上画结构,整个链路是:ELN 里画结构 → 注册到 CMS → 断言 SMILES 结构式正确。"

6. UI+接口混合 ★★

config/setting.py 集中管理 30+ 个业务接口常量;用 page.request 复用登录态直接调接口:创建模板、查项目 ID、删数据。UI 断言 + 接口加速。

7. 全局业务链路编排 ★★

@pytest.mark.order(1~66):模板管理 → 库位容器 → 权限 → 编号规则 → 审核 → 注册 → 样品 → 申领 → 出库 → 导出 → ELN,全链路按业务顺序执行。

8. 自定义异常分层 ★

config/Expection.py:EnvironmentConfigError / ElementNotFoundError / APIResponseError / TestFailedError。断言失败统一 logger.error 详情 + raise,而不是裸 assert。

9. Allure 分层 + 日志 ★★

  • epic/feature/story 三级 + @allure.step 包装关键步骤(如"indraw编辑"、"获取响应")
  • utils/log.py:file + console 双 handler、级别分离(文件 DEBUG 全量/控制台 INFO)、格式带文件名+行号、防重复初始化

10. 一键运行 ★

main.py:运行 pytest → 收集 Allure 结果 → 自动生成报告 → 清理旧报告。python main.py 一条命令全搞定。
